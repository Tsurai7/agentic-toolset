## Problem Statement

The user's ask (2026-07-02): *"координальное усиление перфоманса моделей (haiku, opus,
sonnet), улучшение производительности с меньшим количеством используемых токенов …
использование модели поумнее для принятия решений и планирования и модели попроще для
реализации простых задач."*

Session #1 answered the **policy** half: the on-demand `model-orchestration` skill states
*when* to plan strong / execute cheap / escalate. What it did not ship is the **machinery**:
today every actual delegation is a hand-authored prompt, and the model pins live in the
orchestrator's head. The proven plan-then-delegate practice (two full waves executed in
June–July 2026) exists only as session memory and improvisation — not as repo artifacts.

## Status Quo (Q2 — the real competitor)

What the user does today to get plan-strong/execute-cheap, and what it costs:

| Existing piece | Where | Gap it leaves |
|---|---|---|
| Routing policy skill | `core/skills/model-orchestration/SKILL.md` | Advice, not machinery — nothing enforces or reuses it |
| Plan-then-delegate practice | orchestrator session memory only | Dies with the session/machine; invisible to a fresh clone |
| Delegation prompts | re-authored by the **strong** model each time | ~40 lines of near-identical boilerplate per delegation (scope guard, AC discipline, status protocol, honesty rules, hook/env notes) — measured in the July 2 wave, where the same blocks were re-typed for every agent |
| Model choice per sub-task | remembered, not pinned | A forgotten pin silently runs mechanical work on the expensive tier |
| Cheap-model failure modes | corrected after the fact | Haiku overstated CHANGELOG claims in the July wave; agents died mid-run and relaunches needed hand-built done/remaining maps — the countermeasures are folklore, not config |

The status quo is not "no orchestration" — it is *manual* orchestration that works but
leaks strong-model tokens on boilerplate and does not survive context loss.

**The repo's own audit already asked for this.**
[`current-design-critique.md`](../../docs/research/current-design-critique.md) (row 4 and
"Reframe `model-orchestration` to what's actionable") concluded the skill should "lean on
**subagent fan-out with model overrides** (Claude Code supports per-subagent model) …
not an implied in-prompt model switch." This wedge is that recommendation made concrete —
shipped role definitions ARE the model-override mechanism as durable config. (Credit where
due: the design initially re-derived this independently; the cold-read reviewer spotted
the un-cited lineage.)

## Narrowest Wedge (Q4 — ship this week, not a platform)

Convert the proven manual practice into repo artifacts. Three pieces:

1. **Agent role definitions** in `core/agents/` — `implementer` (mid tier),
   `doc-writer` (cheap tier), `verifier` (mid tier), `researcher` (mid tier + web) —
   with Claude Code subagent frontmatter (one-line description, tool allowlist, `model`
   pin) and bodies carrying the boilerplate that today gets re-typed: scope guard,
   "AC = definition of done", completion-status protocol
   (`DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT`, adopted from gstack), honesty
   rules for reports, and the environment notes (compression hook, retry-blocked-reads,
   never commit unless the plan says so).
2. **Render pipeline**: `providers/claude/install.sh` places them into
   `~/.claude/agents/` exactly like it already renders skills — idempotent, `--eject`-able,
   dry-run visible. Cursor has no subagent equivalent → documented as Claude-only.
3. **Skill upgrade**: a "Delegation protocol" section in `model-orchestration` describing
   the wave mechanics that two waves proved out (plan files with hard AC + file-scope
   separation, verify-per-wave, relaunch-on-death with a done/remaining map, orchestrator
   diff-checks cheap-model claims), pointing at the roles instead of restating them.

Explicitly **out of scope** (unchanged from session #1, plus new rejections): a runtime
router, telemetry pipelines, auto-switching, and per-model *prefix* overlays (see P5).

## Constraints

- **Always-on budget is sacred.** `bin/prefix-budget.sh` must keep passing; nothing here
  may grow `~/.claude/agentic-cfg.generated.md`. Known honest cost: installed agent
  descriptions enter the Agent tool's type list, so descriptions are capped ≤ 25 words
  (~120 tokens total for 4 agents) and bodies carry everything else (pay-per-spawn).
- **Repo conventions**: author in `core/`, render via `providers/*`, every skill change
  keeps eval coverage (`evals/lint.py` gate), deterministic checks go in `bin/ci-check.sh`.
- **Verification-first culture**: the roadmap's acceptance rule (benchmark cells) applies
  to *performance claims*; this wedge claims only mechanization + token arithmetic, both
  checkable without a benchmark run.
- **Weak tier.** Agents install on all tiers, which puts ~120 tokens of descriptions
  into any orchestrating session's context. Stated assumption: in this config's usage
  the weak tier is an *executor* profile (it runs delegated sub-tasks; it does not
  orchestrate), so the cost lands on strong/mid orchestrators that recoup it after one
  delegation (P1). This is an assumption, not a measurement — recorded per the repo's
  weak-tier lesson; revisit with a benchmark cell if a weak-orchestrator use ever
  appears (spec-review finding #4).

## Premises

1. **P1 — Boilerplate arithmetic (measured, small-n).** Counted on this session's two
   live delegation prompts (WS-C, WS-D): the task-independent boilerplate blocks (scope
   guard, honesty rules, environment notes, report shape) are ~200–215 words each
   ≈ **200–300 tokens re-authored by the strong tier per delegation** (word count × 1.3).
   The earlier "300–600" figure from the July wave is anecdotal and is downgraded to an
   unverified upper range. Two honest caveats: (a) n=2 prompts, one author; (b) role
   descriptions cost ~120 always-on tokens, so the win nets out after roughly one
   delegation per session — the wedge's primary value driver is **P3 (portability) plus
   harness-enforced pins**, not this delta. A side-by-side measurement is an explicit
   follow-up (Open Questions).
2. **P2 — The format is real. CONFIRMED** against the official sub-agents doc
   (code.claude.com/docs/en/sub-agents.md, fetched 2026-07-02): user-level files in
   `~/.claude/agents/`, required `name` + `description`, optional `tools`
   (comma-separated allowlist) and `model` (`sonnet`/`opus`/`haiku`/`fable`/full
   ID/`inherit`, default `inherit`). Project-level `.claude/agents/` outranks user-level —
   fine here (this repo renders personal global config). We deliberately use only these
   four keys; the schema's extras (`memory`, `skills` preload, `effort`, `hooks`, …) are
   out of wedge scope. Name collisions: the four role names were checked (2026-07-02)
   against the built-in/session agent types (`general-purpose`, `Explore`, `Plan`,
   `claude`, `claude-code-guide`, `statusline-setup`) — no collision; a future built-in
   collision costs a cheap rename since nothing else hard-codes the names.
3. **P3 — The repo is the right home.** Its stated purpose is "source of truth for
   personal agent config"; session memory is machine-local and lossy. A fresh clone +
   `bin/install.sh` should reproduce the whole workflow.
4. **P4 — Overlay content belongs in role bodies, not the prefix.** gstack ships per-model
   behavioral patches injected into every skill preamble (always-on cost per skill run).
   The same content placed in an agent-role body costs tokens **only when that role is
   spawned** — and the role already fixes the model, so the patch always matches. This is
   the session's Layer-3 point: keep per-model tuning pay-per-spawn.
5. **P5 — rejected premise.** "Per-model prefix overlays would strengthen Haiku/Sonnet/Opus"
   — rejected: it grows the always-on layer for every session, the repo's own history
   (W1 falsified; effort-dial null result) shows environmental additions must be measured
   before shipping, and the Haiku-honesty patch has a cheaper home (the `doc-writer` body).

## Cross-Model Perspective

- **Steelman:** "Promote a manual practice that already worked twice into config, so it
  survives past the current session instead of being re-invented by the next expensive

  everywhere' — applied to a workflow instead of a rule."
- **Key insight:** `current-design-critique.md` row 4 already named subagent fan-out with

  already told them what to build."
- **Challenged premise:** P1 — the 300–600-token figure was uncounted, "exactly that kind
  of unlicensed claim, produced by the same team that wrote the license," and the success
  criteria verified mechanization, not the motivating arithmetic.
- **48h prototype:** measure real boilerplate first; ship `implementer` alone to prove
  the render pipeline; A/B one delegation; extend to the other three roles only after
  the measured delta lands ("each is now a copy-paste-and-adjust, no new plumbing").

**Synthesis (orchestrator):** Accepted — the critique citation is now in Status Quo, P1
is restated with a measured-on-this-session number and an explicit follow-up, and docs
wording is constrained to mechanization-only claims. Partially rejected — we ship all
four roles in one wave, not one: the reviewer's own analysis concedes roles 2–4 add no
new plumbing, the four roles map 1:1 onto the delegations the user already runs (code,
docs, verification, research), and the value driver is portability + pins (P3/P4), which
does not hinge on P1's magnitude. The user's standing workflow request covers the full
set; splitting it across waves would add coordination cost for no risk reduction.

## Approaches Considered

### Approach A: Skill-only upgrade (minimal viable)
Summary: fold the delegation protocol into `model-orchestration`; ship no agent files.
Effort: S. Risk: Low.
Pros: zero new surface; zero always-on cost; smallest diff.
Cons: boilerplate still re-authored per delegation; no model pins; nothing enforces tool
allowlists; the practice still dies with session memory.
Reuses: existing skill + eval cases.

### Approach B: Agent roles + render + skill upgrade (narrowest complete) — RECOMMENDED
Summary: the three-piece wedge above; mechanize exactly what two waves already proved.
Effort: M. Risk: Low–Med (P2 format confirmation; render idempotency must reuse existing
install machinery rather than invent new).
Pros: strong-model tokens stop paying for boilerplate; pins + allowlists enforced by the
harness; portable across machines/clones; per-model guardrails land pay-per-spawn (P4);
evals + ci-check keep it honest.
Cons: ~120 always-on tokens of agent descriptions; Claude-only (Cursor lacks subagents);
four more artifacts to maintain.
Reuses: install render pipeline, evals harness, gstack's status protocol, the July wave's
battle-tested prompt blocks.

### Approach C: Full workflow mechanization (ideal architecture, deferred)
Summary: plan-file templates + a `bin/agentic delegate` prompt generator + schema-enforced
JSON hand-offs (roadmap #8) + stop-hook verification gate (roadmap #6).
Effort: L–XL. Risk: Med–High.
Pros: strongest guarantees; closes the remaining failure modes mechanically.
Cons: builds machinery ahead of measurement — #6/#8 explicitly wait on correctness suite
#0 per the [roadmap](../../docs/research/improvement-roadmap.md); a CLI generator is
speculative surface nobody asked for yet.
Reuses: would build on B; B is a strict prerequisite.

**RECOMMENDATION: B** — it converts a *proven* manual practice into config (the repo's
whole job), adds nothing speculative, and keeps the always-on cost near zero. A is a
subset that leaves the expensive leak (boilerplate re-authoring) open; C is architecture
attachment until the roadmap's instrument exists.

## Open Questions

- Per-agent context cost: the official doc frames subagent context as isolated and does
  not state a per-description cost in the parent; *observed* behavior (this session's own
  system prompt) is that installed agent types are listed with their descriptions in the
  orchestrator's context. We treat the observed cost as real — hence the ≤ 25-word
  description cap — and note the doc/observation gap rather than assert either way.
- Should `researcher` be haiku for cheap sweeps? No — web synthesis with citation
  discipline failed cheap tiers before (June guide work); start mid, revisit with data.
- **Follow-up measurement (from the cold read):** run one real delegation twice — role
  artifact vs hand-typed prompt — and diff the strong-model token count in the
  transcripts. Until then, no doc in this repo states a token-savings number for the
  roles as fact (mechanization-only claims). Candidate home: a `PLAYBOOK`-style micro-eval
  alongside roadmap item 8.
- The `verifier` role addresses the same failure mode as roadmap #6 (stop-hook
  verification gate) by process rather than mechanism; #6 stays parked behind correctness
  suite #0 — the role does not replace it and must not be claimed to.

## Success Criteria

1. **Both install surfaces know about agents.** (a) Shell path:
   `bash bin/install.sh --provider claude --dry-run` lists the agent render; a real run
   symlinks `~/.claude/agents` → `core/agents` (valid frontmatter, `model` pins);
   re-running changes nothing. (b) Go path: `internal/lifecycle` `Inject` links agents
   the same way (backing up a real user dir to `agents.pre-agentic`), `Eject` removes
   the symlink and restores the backup, `Status` reports an `agents` line — mirroring
   the existing skills semantics, with test coverage. Shipping only (a) would leave
   `agentic eject`/`status` silently blind to the new surface (spec-review finding #1).
2. Every agent description ≤ 25 words; bodies carry scope guard, AC discipline, status
   protocol, honesty rules, env notes.
3. `model-orchestration` gains the Delegation-protocol section (points to roles, does not
   restate them); `evals/lint.py` still passes with its cases intact/updated.
4. `bin/prefix-budget.sh` unchanged and passing — the always-on prefix did not grow.
5. `bin/ci-check.sh` gains a deterministic agents-validation section (frontmatter keys,
   description length, name uniqueness) and stays green end-to-end; `go test ./...` and
   `golangci-lint run` stay green.
6. Docs updated without overstatement: `docs/README.md` rows, `CHANGELOG.md` entry,
   `README/ARCHITECTURE` mentions where structure is described.
